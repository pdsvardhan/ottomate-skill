# Onboarding Modes — Bringing Existing Projects to v3

The 14 projects already in Ottomate need to onboard onto the new skill. Four modes per project, plus a recommended order to minimize risk.

**Goal:** every project ends up at a known stage with valid SO1 docs (or explicitly archived). No silent migrations; no destructive ops on existing data.

---

## The 4 modes

| Mode | What | When to use |
|---|---|---|
| **Lite** | Fill `manifest.yaml` only. Mark `needs_stage_1_catchup: true`. Skip Stage 1 detail. Direct Stage 4 entry. | Shipped/stable projects you don't iterate on |
| **Standard** | Backfill all 7 SO1 docs from existing artifacts. Run 5-pass verification. Mark Stage 1 complete. | Active projects you iterate on (DEFAULT) |
| **Full** | Standard + Stage 2 backfill. Generate `ui-master-plan.yaml` from existing tokens, `tech-stack.yaml` from `package.json`, architecture diagram from code structure. | Portfolio showcase / interview-ready projects |
| **Archive** | Don't migrate. Old project row in Ottomate stays as historical reference. | Dead/abandoned/empty projects |

## Onboarding workflow per project

Per locked design at CC-6:

### 1. Inspect
Read existing project row in Ottomate + project repo's CLAUDE.md / decisions/ / package.json / code structure.

```bash
# On server
cat /mnt/storage/websites/<slug>/CLAUDE.md
ls -la /mnt/storage/websites/<slug>/decisions/
cat /mnt/storage/websites/<slug>/package.json
find /mnt/storage/websites/<slug>/app -type f | head -20
```

### 2. Classify state
Compute observable target stage from inspection results:
- Has tests + deployed + recent commits → past Stage 3
- Has package.json + scaffold + few features → mid Stage 3
- Has CLAUDE.md but no code → Stage 1 / 2
- Has nothing meaningful → Archive

### 3. Propose mode
Skill proposes mode based on classify; user confirms via AskUserQuestion:

```
PROJECT: cricket-stats

Detected state:
  · Repo at /mnt/storage/websites/cricket-stats/ (well-developed)
  · Container running on port 8101
  · Tests: 12 Playwright specs, 8 Vitest unit
  · CLAUDE.md present (12K), 4 ADRs
  · package.json: Next.js 15 + better-sqlite3 + Recharts

Suggested mode: Full (interview-ready portfolio)
  · backfill 7 SO1 docs from artifacts
  · backfill ui-master-plan from existing Tailwind tokens
  · backfill tech-stack from package.json
  · generate architecture diagrams from code structure

Confirm mode:
  [ Full (Recommended) ]   [ Standard ]   [ Lite ]   [ Archive ]   [ Cancel ]
```

### 4. Backfill per mode

**Lite:**
- Read minimum from existing: slug, display_name, port, public_url, tagline (compose from CLAUDE.md)
- Fill `manifest.yaml` only
- Mark `needs_stage_1_catchup: true`
- Skip everything else
- Direct Stage 4 entry on next session

**Standard:**
- Run **Stage 0 catchup (T2P-style)** — treat existing repo as F1 + CLAUDE.md as F2 + decisions/ as F2
- Doc translation extracts what it can to ND1
- User dialog fills gaps (problem_statement might already be in CLAUDE.md; success_criteria probably needs user input)
- Run Stage 1 normally → produces all 7 SO1 docs
- Run Stage 1.9 5-pass verification
- Mark Stage 1 complete

**Full:**
- Standard backfill
- Plus Stage 2 backfill:
  - `ui-master-plan.yaml` generated by reading project's Tailwind config + extracted CSS variables (Claude composes from real tokens)
  - `tech-stack.yaml` generated from package.json + tsconfig + drizzle.config (Claude composes)
  - `architectures.yaml` generated by Claude reading file tree + import graph (Mermaid sources)
  - `build-plan.yaml` reverse-engineered from git history (which features landed in which order; Claude composes)
- All Stage 2 verification at 2.8

**Archive:**
- Mark old project row in Ottomate `archived=true` + `archive_reason`
- Don't create new SO1 docs
- Removed from default project list (filterable)
- Existing repo on disk untouched

### 5. Verify
For Standard / Full: run Stage 1.9 (and 2.8 if Full). HARD halts have sub-step pointers; user iterates on dialog gaps.

### 6. Stage placement
Write target stage to Ottomate. Project ready for Stage 4 iteration.

### 7. Iteration log + ADR
Record onboarding event: `decisions/<date>-onboarded-from-v2.md` ADR with mode + backfill summary + special handling notes.

## Special handling

### Projects with active blockers (health, ingest)
The blocker becomes the FIRST Stage 4 iteration item:
- health DB-empty → iter-1 item: `risk_addition: data ingestion not yet wired`
- ingest RCS blocker → iter-1 item: `bug: RCS endpoint returning 401`

Standard onboarding completes; first Stage 4 iteration immediately tackles the blocker.

### Discovery-only projects (desi-skies, paata)
These have minimal artifacts (just a CLAUDE.md sketch). Re-run **new** Stage 0 fresh:
- Treat old CLAUDE.md as F2 doc input (Type 2 path)
- Old decisions/ as F2 doc input
- 0.3 doc translation extracts whatever it can
- 0.4-0.10 fills gaps via dialog
- Outcome: clean ND1 + Stage 1 → Stage 2 → ready for build

### Existing repos at `/mnt/storage/websites/*` stay untouched
New SO1 mirrors generated alongside existing files. Old `decisions/` directory preserved (acquires new ADRs from onboarding event but doesn't lose history).

### Bug data migration
`reports`, `bugs`, `feature_requests` tables — migrate as-is from old tracker (one INSERT per row). Likely small volume since old Ottomate had no UI.

## Failure isolation

Per CC-6 D-CC6.3, onboarding failures isolated per project:
- `onboarding_status: failed` written to project row with reason
- Skip and continue with next project
- Failed projects can be retried in a future session
- Don't block other projects' onboarding on one failure

---

## Risk mitigation

- Old project row in Ottomate preserved in `archive/v2-rows/` table (tagged, not deleted)
- Onboarding is read-mostly from old data — no destructive ops
- Each project's onboarding is its own DB transaction; rollback on failure
- v2 Ottomate keeps running on whatever port until v3 cutover
- DB backup before mass migration: `POST /api/backup` (per existing API)
