## WS1.1 — Live preview engine (Ottomate-hub live iframes) — fixes F-14 + F-10
Replace the JS-inert static DSD panel with a **real, running** render of each variant, **inside the Ottomate
hub** (owner decision). **Brainstorm outcome (`docs/plans/2026-07-29-WS1.1-live-preview-design.md`): use the
app's OWN proven `sandbox="allow-scripts"` iframe pattern, NOT Sandpack** — the app already tried Sandpack and
moved off it (iter-77), and already renders live JS/motion in iframes; F-14's real cause is the harness
emitting script-less DSD, not the frame. No external research needed. Build = (1) emit interactive
token-themed self-contained HTML per variant, (2) a grid of full-width per-variant live iframes in
`RoundPicker`. Needs an Ottomate-app deploy (confirm before deploying live).
- Embed an **in-browser code sandbox** (Sandpack, or Nodebox for heavier deps) in the Ottomate design page.
  Each variant is a self-contained bundle that **runs live** — real hover / motion / 3D / charts — reading
  the project's **semantic-token theme sheet** (Phase 0's `cointrail.theme.css`) so it themes correctly and
  the contrast gate governs.
- The design surface shows a **grid of live sandboxes**, one per variant, **full-size** (fixes F-10's
  squeezed compare view — each wide variant gets its own frame). A postMessage bus for "interact all" /
  viewport sync (stretch; single-frame interactivity first).
- **Open design questions (brainstorm first):** how a variant declares its deps + entry; how real project
  components are pulled into the sandbox vs authored self-contained; CSP/security of running code in the hub;
  drafts (pre-commit) vs committed. **Research flagged:** Sandpack/Nodebox integration + CSP (see §Research).
- **Acceptance:** for a ≥2-variant round, the owner opens **one** Ottomate URL and each variant renders
  **live** (a hover/animation/3D effect actually runs) at **full width**, side by side, themed by the project
  tokens.
- **Verify:** drive it in real Chromium — capture a variant mid-interaction (hover changed, a number counted
  up); render the grid light + dark; the hub URL returns 200 from a client.
- **Later (not Phase 1):** a project-side `/design-mode` route for perfect-fidelity real-data preview.

## WS1.2 — Legibility banner — fixes F-17 (the owner's sharpest complaint)
Every round leads, in plain language, with **what it decides and what is held**.
- The round packet computes and the surface renders, LOUD and first (never a buried subtitle):
  **"This round decides: [X, Y]. The N versions differ ONLY in that; everything else is held. Pick one or
  mix."** — enumerated from the round's actual contested axes + the frozen controls.
- **No silent deferrals:** if an axis (e.g. motion) is pushed to a later round, the banner says so and the
  flow gets explicit assent — never a silent "round 2."
- **Acceptance:** a published round's page states, in a prominent banner, the exact axis/axes it decides and
  names what is held constant; a deferral is stated and assented to, not silent.
- **Verify:** render a round; show the banner text is generated from the round's real axes (not hand-typed);
  a must-show negative — a round that tries to defer an axis without assent is flagged.

## WS1.3 — Decompose-and-ask for one Block + always-ask scope — fixes F-15 (+ F-4, F-9)
On "redesign X," **decompose first, then ASK** — never silently choose scope.
- On a redesign request, inspect the real component and present its **anatomy** (Section → changeable
  dimensions: layout, type, data-presentation, Behaviors), driven by the anatomy graph + `data-role`/
  `data-oid` stamping (Phase 0's Block is already stamped), **not name-guessing** (F-4).
- **Always ask** (owner ruling): *which* sub-structure (whole Block / one Section / one property) and *how
  deep*, via an explicit `AskUserQuestion` — anything from a font to a border animation. Then variants
  explore **that** — one-property cycles OR whole directions by the owner's explicit choice (F-9).
- **Acceptance:** given a real Block, the tool lists its decomposable parts and **asks** what to change +
  at what granularity before generating; the chosen scope drives what varies vs what's held (feeds WS1.2).
- **Verify:** run the decomposition on the cointrail category-breakdown Block; show the parts list came from
  the anatomy/`data-role` (not a name heuristic) and the scope question was asked, not assumed.
