# Task 3 — Feature Verifier: self-contained brief for the parallel session

**Written 2026-07-28.** Supersedes `2026-07-27-TASK3-PARALLEL-SESSION-BRIEF.md` (which is still valid
for its WP detail, but predates A4/A5). A cold Task-3 session can start from this doc alone.

## What it IS
A **second, independent verifier** that sits beside the existing code verifier as a Stage-3.5 / Stage-4.7
gate. The code verifier proves the CODE (reads the diff, runs the coder's happy-path tests). The
**feature verifier drives the REAL running app like a QA human** and asserts **system state** — the row
that landed in the DB, the file that appeared on disk, the async job that completed — with evidence
(trace / video / screenshot) attached. Both gate "done" for user-facing features (block cv/public,
warn personal).

## WHY we're building it / what it SOLVES
The gap it closes is the one the owner hit repeatedly: *"the coder says it works, the happy-path test is
green, and the feature is still broken."* A code-only verifier cannot catch: a POST that returns 200 but
writes nothing; a file upload that silently drops non-ASCII (Telugu/Tamil) filenames; an async pipeline
that never completes; a UI that renders but whose control does nothing. The feature verifier asserts the
*effect*, not the *response code* — and it does so from an **independent** agent that never sees the
coder's claims, so it cannot be gaslit by them. It is the Task-1/Task-2 "evidence + fail-closed + lock-in"
discipline applied to *"did this feature actually work end to end?"*
