# WS1.1 — live preview design note (brainstorm outcome) · 2026-07-29

**Goal (owner decision):** a live, interactive preview of each round's variants **inside the Ottomate hub**
— real hover / motion / 3D / charts, not a dead screenshot (F-14), each variant full-size (F-10).

## Key finding — Sandpack is NOT needed (grounded in the real app)
The owner picked "in-browser sandbox (Sandpack)", but inspecting the running Ottomate app changed the answer:

1. **The app already had Sandpack and deliberately moved OFF it** (`components-browser/[id]/LivePreview.tsx`,
   iter-77: *"manifest-driven preview … replaces the Sandpack CDN bundler"*). Reintroducing it would re-adopt
   something the owner already rejected as flaky.
2. **The app already renders live components in a sandboxed iframe** — two proven house patterns:
   - a prebuilt bundle served from `/api/previews/<id>/index.html` in an `<iframe sandbox="allow-scripts">`;
   - a `srcdoc` iframe built from self-contained HTML/CSS/JS (inlines CSS, injects CDN libs like gsap/three).
   Both **run real JavaScript, motion and 3D today** in the components browser.
3. **F-14's real cause is the CONTENT, not the frame.** The design round's `RoundPicker` already puts the
   published HTML in an iframe (`src={preview_url}`) — but the **harness emits static declarative-shadow-DOM
   panels with no JS**, so there is nothing to animate. The iframe can run scripts; the page has none.
4. **F-10's real cause** is that one iframe shows all N variants squeezed side-by-side inside a single page.

**Conclusion:** deliver the owner's goal with the app's OWN proven pattern — self-contained interactive HTML
in `sandbox="allow-scripts"` iframes — not Sandpack. Lower risk, no new dependency, no external research.

## The build (two changes, both in the Ottomate hub)
1. **Content — emit INTERACTIVE, token-themed, self-contained HTML per variant.** Reuse Phase 0's
   `blocks/category-breakdown.html` shape: real JS (count-up, bars grow, hover-lift, 3D), reading the
   project's `[data-theme]` token sheet, honouring `prefers-reduced-motion`. One file per variant. This
   replaces the JS-inert DSD emit (the harness/preview-build side).
2. **Surface — a GRID of per-variant live iframes in `RoundPicker`.** One `<iframe sandbox="allow-scripts">`
   **per variant**, each full-width (fixes F-10's squeeze), laid out in a responsive grid, each labelled with
   the variant's letter/name. A "replay" remount (already exists in LivePreview) re-fires on-load motion.
   Stretch: a postMessage "interact all" bus + viewport sync.

## Open sub-questions (small, not blockers)
- Per-variant HTML file layout on the previews volume: `.../rN/v1.html`, `v2.html`, … + the existing
  `index.html` as a fallback all-in-one. (Backwards compatible — old rounds still show their index.html.)
- Drafts (pre-commit): the srcdoc path already renders un-published HTML, so an AI draft can preview before
  it is written to the volume. Covers the owner's "works for drafts not in a project yet" want.

## Research flagged for the owner (only if we want the richest path later)
- **None required for this build.** (Sandpack/Nodebox research is now moot — house pattern wins.)
- *Optional, later:* if a variant needs the project's REAL React components (not self-contained HTML), that's
  the project-side `/design-mode` fidelity upgrade — a separate, later track.

## Acceptance (unchanged) + verify
- For a ≥2-variant round, the owner opens one Ottomate URL and each variant renders **live** (an effect
  actually runs) at **full width**, side by side, themed by the project tokens.
- Verify: drive it in real Chromium — capture a variant mid-interaction; grid light + dark; hub URL 200.
